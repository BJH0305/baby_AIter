# 질의응답 준비 (3분)

> 질의는 3분이라 질문 3~4개가 들어온다. 답변은 **30초, 4문장**: 결론 → 근거 → 한계 인정 → 계획.
> 담당: 기술 질문 = A(빌더), 기획·근거 질문 = B(기획·기록), 기대 효과·확장 = C(발표). 셋이 한 번씩은 답한다 (협업 기여도).
> 기능별 질문은 `FEATURE_CATALOG.md`, 우리 서비스 맞춤 질문은 `spec.md` 8번에 있다.

## 답변 공식 예시

> Q. 로그인 기능은 보안이 되나요?
> (결론) 시연판은 비밀번호 없는 데모 계정으로 구현했습니다.
> (근거) 1박 2일 프로토타입에서 비밀번호를 직접 저장하는 건 오히려 보안상 위험하다고 판단했습니다.
> (한계) 그래서 지금은 기기 안에서만 데이터가 분리됩니다.
> (계획) 실서비스는 Supabase Auth로 비밀번호를 해시 저장하고, DB 접근 권한 규칙으로 본인 데이터만 읽게 합니다.

"모르겠습니다"보다 "지금은 이렇게 했고, 실서비스는 이렇게 하겠다"가 항상 점수가 높다. 한계를 먼저 인정하면 실현 가능성 점수가 오른다.

## AI 활용 (거의 반드시 나옴)

- **Q. 코드를 AI가 다 짠 건가요? 직접 이해하나요?**
  A. 기능 정의, 화면 흐름, 데이터 구조는 저희가 먼저 문서로 정했고 Codex는 그 문서를 보고 코드를 생성했습니다. 생성된 코드는 화면별로 직접 확인하고 수정 지시를 반복했습니다. 예를 들어 [실제로 고친 사례 1개]는 저희가 원인을 찾아 고쳤습니다. 커밋 기록 n개에 그 과정이 남아 있습니다.
  → A는 현장에서 실제로 고친 사례 1개를 꼭 기억해 둔다.
- **Q. 구조를 설명해 보세요.**
  A. 화면은 HTML 섹션 단위, 화면 전환은 주소의 해시 값으로 바꾸는 방식, 데이터는 `data.js`의 배열을 브라우저 저장소에 저장합니다. [핵심 기능]은 [함수 이름]에서 [규칙]으로 계산합니다. (`docs/tech-notes.md` 참고)
- **Q. AI를 어디에 썼나요?** (개발 / 서비스 안 두 가지로 나눠 답한다)
  A. 개발에서는 Codex로 구현 속도를 높였고, 서비스 안에서는 [기능]에 AI를 적용할 계획입니다. 프로토타입은 규칙 기반으로 결과 흐름을 먼저 검증했습니다.

## 기획

- **Q. 비슷한 서비스가 이미 있지 않나요?** → 기존 서비스 1~2개 이름 + "그 서비스는 [무엇]이 없어서 [대상]이 못 쓴다" 한 줄.
- **Q. 실제로 쓸까요?** → 행사장에서 받은 짧은 의견(다른 팀 참가자, 멘토 n명)을 숫자로. 없으면 근거 통계.
- **Q. 누가 돈을 내나요? 어떻게 유지하나요?** → 지자체·학교·기관 도입(B2G/B2B), 공공 사업 연계. 한 문장.
- **Q. 전공이 어떻게 합쳐졌나요?** → 팀원별 한 문장. "OO학과 관점에서 [무엇]을 넣었다."

## 기술

- **Q. 개인정보는?** → 수집 항목 / 저장 위치 / 접근 권한 / 삭제 방법, 각 한 문장. 프로토타입은 서버로 보내지 않는다는 점 강조.
- **Q. 데이터 출처는?** → 공공데이터포털 등 실제 이름. 예시 데이터라면 "실제 [출처] 형식을 본떠 만든 예시"라고 정직하게.
- **Q. 왜 앱이 아니라 웹?** → 설치 없이 링크·QR로 바로 접근, 대상 사용자의 진입 장벽, PWA 확장.
- **Q. 사용자가 늘면?** → 정적 배포는 CDN, DB는 관리형 서비스로 확장.
- **Q. 오류가 나면? 예외 처리는?** → 빈 입력·잘못된 입력·결과 없음 화면을 넣었다고 답하고 바로 시연할 수 있으면 보여준다.

## 하면 안 되는 답

- "시간이 부족해서요" (→ "프로토타입 범위를 [무엇]에 집중했습니다")
- "AI가 해서 잘 모르겠습니다"
- 없는 기능을 있다고 말하기 (심사위원이 시연을 요청하면 끝)
