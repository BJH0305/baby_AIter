# 기능 카탈로그

> 아이디어가 정해지면 여기서 기능을 **핵심 3개 + 보조 1~2개**만 고른다.
> 각 기능은 두 단계로 나눠 두었다.
> - **Lv1 (시연용)**: 서버 없이 브라우저만으로 동작. 30분~1시간. 실패 확률 낮음.
> - **Lv2 (실제 동작)**: 외부 서비스·라이브러리 연동. 1~2시간. 인터넷 필수, 실패 시 Lv1로 후퇴.
>
> 원칙: 핵심 기능 1개만 Lv2로 올리고 나머지는 Lv1. 실현형 최우수상(기획+구현+발표)을 노릴 땐 "한 기능은 진짜로 동작한다"가 강력한 무기다.
> `prompts.md`의 "아이디어 → 명세" 지시문이 이 파일을 읽고 `docs/spec.md`를 만든다.

## F01 로그인·회원

- **필요할 때**: 사용자마다 다른 데이터를 보여줘야 할 때 (내 기록, 내 신청 내역)
- **Lv1**: "데모 계정 선택" 화면. 프로필 카드(학생 / 보호자 / 관리자 등)를 누르면 그 사람으로 로그인. 현재 사용자는 `localStorage`에 id만 저장. **비밀번호 입력칸은 만들지 않는다** (가짜 비밀번호 저장은 보안 질문에서 약점).
- **Lv2**: Supabase Auth (이메일 매직링크 또는 이메일+비밀번호). CDN으로 `supabase-js` 불러오기. 프로젝트 URL과 anon key 필요.
- **시연 포인트**: 계정을 바꾸면 화면 내용이 바뀌는 장면 (학생 → 관리자).
- **예상 질문**
  - Q. 비밀번호는 어떻게 저장하나요?
    A. (Lv1) 시연 편의를 위해 비밀번호 없는 데모 계정으로 바꿨습니다. 실서비스는 비밀번호를 우리가 직접 저장하지 않고 Supabase Auth 같은 검증된 인증 서비스를 씁니다. 비밀번호는 bcrypt로 해시되어 저장되고, 로그인 후에는 JWT 토큰으로 세션을 유지합니다.
    A. (Lv2) Supabase Auth가 bcrypt 해시로 관리하고 저희 코드에는 비밀번호가 남지 않습니다.
  - Q. 다른 사람 데이터를 볼 수 있지 않나요?
    A. DB의 Row Level Security로 "로그인한 사용자 id와 데이터 작성자 id가 같을 때만 읽기"를 DB에서 강제합니다. 프론트엔드 코드를 조작해도 막힙니다.
  - Q. 프론트에 키가 노출돼 있는데요?
    A. 공개용 anon key라 노출을 전제로 설계된 키입니다. 실제 권한은 RLS 정책이 막고, 관리자 키(service role)는 프론트에 두지 않습니다.
  - Q. 소셜 로그인은요?
    A. 실서비스 1단계에서 카카오 로그인을 붙일 계획입니다. 대상 사용자가 가장 많이 쓰는 계정이라 가입 이탈을 줄입니다.

## F02 데이터 저장

- **Lv1**: `localStorage` (스타터 키트 기본). 새로고침해도 유지. 시연용 초기화 기능 포함.
- **Lv2**: Supabase DB 테이블 1~2개. 여러 기기·여러 사람이 같은 데이터를 보는 장면이 필요할 때만.
- **예상 질문**
  - Q. 데이터는 어디에 저장되나요?
    A. 프로토타입은 브라우저 저장소에 저장해서 서버 없이 시연합니다. 실서비스는 PostgreSQL 기반 Supabase로 옮기고, 데이터 구조는 지금 코드의 객체 구조를 그대로 테이블로 씁니다.
  - Q. 사용자가 많아지면요?
    A. 정적 웹은 CDN으로 배포돼 접속자가 늘어도 문제가 없고, DB는 관리형 서비스라 사용량에 따라 확장됩니다.

## F03 검색·필터·정렬

- **Lv1**: 입력창 + 칩 필터. `data.js` 배열을 `filter`/`sort`. 초성 검색이 필요하면 간단한 초성 변환 함수.
- **시연 포인트**: 검색어를 치는 즉시 목록이 줄어드는 장면, 결과 없음 빈 상태.
- **예상 질문**: Q. 데이터가 수만 건이면? A. 실서비스는 DB 인덱스와 서버 검색(전문 검색)으로 처리합니다.

## F04 지도·위치

- **Lv1**: 지도 이미지 대신 "가까운 순 목록" + 거리 표시(예: 0.8km). 좌표는 `data.js`에 직접 넣고 하버사인 공식으로 거리 계산.
- **Lv2**: Leaflet + OpenStreetMap (CDN, API 키 불필요). 마커와 팝업. 카카오맵은 앱 키·도메인 등록이 필요해 현장에서 막힐 수 있어 피한다.
- **시연 포인트**: 마커를 누르면 상세 시트가 올라오는 장면.
- **예상 질문**
  - Q. 사용자 위치는 어떻게 받나요? 개인정보 문제는?
    A. 브라우저 위치 권한을 사용자가 허용할 때만 받고, 거리 계산에만 쓰고 서버에 저장하지 않습니다. 시연에서는 창원대 위치를 기본값으로 둡니다.
  - Q. 장소 데이터 출처는?
    A. 공공데이터포털의 [데이터셋 이름]을 사용합니다. (B가 실제 이름 확인)

## F05 추천·매칭

- **Lv1**: 규칙 기반 점수. 예: 관심사 일치 +3, 거리 1km 이내 +2, 시간 겹침 +2 → 점수순 정렬. 결과 카드에 "추천 이유" 한 줄 표시.
- **Lv2**: 같은 점수식에 가중치 조절 슬라이더를 붙여 실시간 재정렬.
- **시연 포인트**: 조건을 바꾸면 추천 순위가 바뀌고 이유 문구가 달라지는 장면.
- **예상 질문**
  - Q. AI 추천인가요?
    A. 지금은 설명 가능한 규칙 기반 점수입니다. 데이터가 쌓이면 협업 필터링이나 임베딩 유사도로 바꿀 계획이고, 규칙 기반부터 시작한 건 초기에는 데이터가 없어 학습 모델이 오히려 부정확하기 때문입니다.
  - Q. 가중치 근거는?
    A. 사용자 인터뷰(현장에서 n명)에서 가장 중요하다고 답한 순서를 반영했습니다.

## F06 AI 챗봇·상담

- **Lv1**: 시나리오 챗봇. 키워드 → 답변 사전(`data.js`) 매칭 + 빠른 질문 버튼 3~4개. 답변 전 "입력 중..." 0.8초.
- **Lv2**: 실제 LLM API 호출은 **키 노출 문제로 프론트에서 하지 않는다.** 시연은 Lv1, 발표에서 구조만 설명.
- **시연 포인트**: 빠른 질문 버튼 → 자연스러운 답변 → 관련 화면으로 이동 버튼.
- **예상 질문**
  - Q. 실제 AI인가요?
    A. 프로토타입은 자주 묻는 질문 n개를 시나리오로 구현했습니다. 실서비스는 서버를 거쳐 LLM API를 호출하고, 우리 서비스 데이터를 검색해서 답하는 RAG 구조로 잘못된 답(환각)을 줄입니다. API 키는 서버에만 둡니다.
  - Q. AI가 틀린 답을 하면 책임은?
    A. 답변마다 근거 출처를 표시하고, 법률·의료처럼 위험한 질문은 전문 기관 연결로 넘깁니다.

## F07 사진 업로드·판별

- **Lv1**: `<input type="file" accept="image/*">` + `FileReader` 미리보기. "분석 중" 1초 후 미리 정한 결과 표시(시연용 사진 2~3장을 미리 준비해 파일명으로 결과 매칭).
- **Lv2**: Teachable Machine으로 현장에서 이미지 분류 모델을 만들고 TensorFlow.js로 불러오기. 인터넷 필요, 1.5~2시간.
- **시연 포인트**: 사진 올림 → 로딩 → 결과 + 다음 행동 안내.
- **예상 질문**
  - Q. 정확도는?
    A. (Lv1) 프로토타입은 결과 흐름을 보여주는 단계입니다. 실서비스는 분류 모델을 학습시켜 검증 데이터 기준 정확도를 측정하고, 확신도가 낮으면 사용자에게 직접 선택하게 합니다.
  - Q. 사진은 어디 저장되나요?
    A. 브라우저 안에서만 처리하고 서버로 보내지 않습니다.

## F08 다국어

- **Lv1**: `i18n` 사전 객체 `{ ko: {...}, en: {...}, vi: {...} }` + 상단 언어 전환. 화면 문구는 전부 사전에서 꺼낸다.
- **시연 포인트**: 언어 버튼 하나로 전체 화면이 바뀌는 장면 (외국인·다문화 주제면 필수급).
- **예상 질문**: Q. 번역 품질은? A. 핵심 문구는 원어민 검수(유학생 등)를 받고, 긴 안내문은 번역 API + 검수 방식으로 확장합니다.

## F09 알림·리마인더

- **Lv1**: 앱 안의 알림 목록 화면 + 상단 종 아이콘 배지 숫자 + 토스트. 시간 흐름이 필요하면 "다음 날로 이동" 같은 시연용 버튼.
- **예상 질문**: Q. 실제 푸시는? A. 웹 푸시(Service Worker)나 카카오 알림톡으로 확장합니다. 알림톡은 미응답률이 낮아 어르신 대상에 적합합니다.

## F10 예약·신청

- **Lv1**: 신청 폼 → 상태 흐름(신청 → 검토 중 → 승인) 배지. 관리자 계정(F01)으로 바꾸면 승인 버튼.
- **시연 포인트**: 사용자 신청 → 관리자 승인 → 사용자 화면 상태 변경. 두 역할을 오가는 장면이 "서비스 완성도"로 보인다.
- **예상 질문**: Q. 중복 예약은? A. 같은 시간대 신청이 있으면 막는 검사를 넣었습니다 (Lv1에서도 구현 가능, 꼭 넣기).

## F11 커뮤니티·게시판

- **Lv1**: 글 목록 / 글쓰기 / 댓글 / 공감 수. `localStorage`.
- **예상 질문**: Q. 악성 글은? A. 신고 누적 시 자동 숨김 + 금칙어 필터. 프로토타입에 금칙어 필터를 넣어 시연할 수 있다.

## F12 통계·대시보드

- **Lv1**: CSS 막대그래프나 Chart.js(CDN). 요약 숫자 3개 + 그래프 1개.
- **시연 포인트**: 기록을 추가하면 그래프가 바로 바뀌는 장면.
- **예상 질문**: Q. 이 통계로 무엇을 결정하나요? A. 지자체·학교가 [무엇]을 판단하는 데 씁니다 (B2G 확장 근거와 연결).

## F13 퀴즈·학습·포인트

- **Lv1**: 문제 배열 → 한 문제씩 → 정답 피드백 → 점수·배지. 오답 노트.
- **예상 질문**: Q. 학습 효과는? A. 반복 퀴즈(간격 반복)의 근거 연구를 인용하고, 실서비스에서 사전·사후 점수로 효과를 측정합니다.

## F14 일정·캘린더

- **Lv1**: 월간 달력 직접 그리기(그리드 7열) + 날짜별 점 표시 + 날짜 누르면 목록. 텍스트에서 날짜 뽑기가 필요하면 정규식(`/(\d{1,2})월\s*(\d{1,2})일/`).
- **예상 질문**: Q. 구글 캘린더 연동은? A. 실서비스에서 .ics 파일 내보내기부터 지원합니다.

## F15 QR 코드

- **Lv1**: `qrcodejs`(CDN)로 QR 생성(입장권·인증용). 스캔은 카메라 권한 문제로 시연에서 제외.
- **예상 질문**: Q. QR 위조는? A. QR에 일회용 토큰만 담고 서버에서 검증하는 구조로 설계합니다.

## F16 관리자 화면

- **Lv1**: F01 데모 계정의 "관리자"로 전환하면 전체 현황 표 + 승인/숨김 버튼.
- 사용자 화면과 관리자 화면이 둘 다 있으면 "운영까지 생각한 서비스"로 보인다. 시간 남을 때 1순위 추가 기능.

## 공통: 어떤 기능이든 들어오는 질문

- **AI(Codex)로 만든 코드를 이해하고 있나요?** → `docs/QNA.md`의 "AI 활용" 답변 참고. 빌더는 `docs/tech-notes.md`의 구조 설명 5줄을 외운다.
- **보안·개인정보** → 수집하는 정보, 저장 위치, 접근 권한, 삭제 방법 4가지를 한 문장씩.
- **왜 앱이 아니라 웹인가요?** → 설치 없이 링크·QR로 바로 쓸 수 있어 [대상 사용자]의 진입 장벽이 낮고, PWA로 홈 화면 추가가 가능합니다.
