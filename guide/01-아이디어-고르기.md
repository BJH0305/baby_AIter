# 01. 아이디어 고르기 (회의 전에 리더가 읽고 들어가기)

> 이 대회의 기획 점수는 **독창성 · 실현 가능성 · 사회적 유용성 · 전공 융합을 통한 문제 접근의 참신성**이다.
> 좋은 아이디어 = 심사위원이 첫 30초에 "아, 그 사람 진짜 불편하겠다"고 느끼고, 시연에서 "이거 바로 쓸 수 있겠네"라고 느끼는 것.

---

## 1. 심사 기준을 질문으로 바꾸면

| 기준 | 심사위원 머릿속 질문 | 통과하려면 |
| --- | --- | --- |
| 독창성 | 처음 보는 접근인가? | "OO 앱 같은 거네"라는 말이 안 나온다. 대상을 좁히거나 관점을 바꿨다 |
| 실현 가능성 | 진짜 만들 수 있나, 누가 쓰나? | 프로토타입이 실제 동작하고, 실서비스로 가는 단계가 한 줄로 설명된다 |
| 사회적 유용성 | 누구의 어떤 문제가 얼마나 줄어드나? | 구체적인 사람 + 근거 숫자 + 줄어드는 양(시간, 비용, 위험) |
| 전공 융합 | 이 팀이라서 나온 아이디어인가? | 팀원 3명 전공이 각자 다른 부분을 맡았다고 말할 수 있다 |

→ 회의 때 후보마다 이 4개 질문을 소리 내서 던진다. 하나라도 답이 막히면 다듬거나 버린다.

## 2. 참신하게 만드는 6가지 방법

평범한 주제도 이렇게 비틀면 독창성 점수가 오른다.

1. **대상을 좁힌다**: "외국인을 위한 앱" → "거제 조선소 입사 3개월 차 외국인 용접공의 안전 교육"
2. **숨은 사용자를 찾는다**: 당사자 말고 옆 사람. 환자 → 보호자, 학생 → 담임 선생님, 어르신 → 멀리 사는 자녀
3. **우리 지역에서 시작한다**: 창원·거제·경남의 문제(조선업, 고령화, 기계산업, 섬·관광, 대학생 자취)는 심사위원이 바로 공감하고, 근거 자료도 지역 통계로 찾기 쉽다
4. **순간을 잡는다**: 서비스 전체가 아니라 "가장 곤란한 5분"만 해결. 예) 병원 가는 날 전체 → 접수 창구 앞에서 증상 설명하는 순간
5. **전공 지식을 무기로 쓴다**: SW는 도구일 뿐이고, 문제를 보는 눈은 다른 전공에서 나온다 (아래 3번 표)
6. **기존 해결책의 빈틈을 찌른다**: "지금은 OO로 해결하는데, 그건 [누구]가 못 쓴다 / [어떤 상황]에서 안 된다"

## 3. 전공 융합 조합 아이디어 씨앗

팀원 전공을 확인하고 가로·세로로 맞춰 본다. 그대로 쓰기보다 출발점으로.

| 팀원 전공 | 그 전공이 보는 문제 | SW로 만들 수 있는 것 |
| --- | --- | --- |
| 교육·사범 | 다문화 학생, 학습 격차, 교사 업무 | 가정통신문 쉬운 말 변환, 수준별 퀴즈, 학부모 다국어 알림 |
| 간호·보건·체육 | 복약 관리, 응급 대처, 고령자 건강 | 복약 체크와 보호자 알림, 응급 상황 단계별 안내 |
| 사회복지·행정 | 복지 사각지대, 신청 절차 복잡 | 내가 받을 수 있는 지원 찾기, 신청 서류 체크리스트 |
| 경영·경제 | 소상공인, 지역 상권, 청년 재무 | 동네 가게 재고 나눔, 자취생 고정비 관리 |
| 국제관계·외국어 | 외국인 근로자·유학생 정착, 문화 차이 | 다국어 생활 안내, 상황별 표현 카드 |
| 환경·건축·토목 | 분리배출, 노후 시설, 안전 | 배출 방법 검색, 위험 시설 제보 지도 |
| 기계·전기·조선 | 산업 안전, 현장 교육 | 작업 전 안전 점검 체크, 현장 용어 학습 |
| 디자인·미디어 | 정보 접근성, 지역 홍보 | 쉬운 정보 시각화, 지역 관광 코스 |
| 컴퓨터·SW | (도구 담당) | 데이터 구조, 추천·매칭 규칙, 시연 안정성 |

→ "OO학과 관점에서 [문제]를 발견했고, ㅁㅁ학과 지식으로 [해결 방식]을 정했고, SW로 [기능]을 만들었다" 한 문장이 나오면 전공 융합 통과.

## 4. 이런 아이디어는 피한다

| 유형 | 왜 위험한가 |
| --- | --- |
| 만능 AI 챗봇 | 10팀 중 여러 팀이 낸다. 실제 AI 연결이 안 되면 시연이 빈약해진다 |
| 일정·할 일 관리 앱 | 이미 너무 많다. 독창성 점수가 낮다 |
| SNS·커뮤니티 일반 | 사용자가 모여야 가치가 생겨서 시연으로 증명이 안 된다 (특정 대상·목적이면 괜찮음) |
| 문제가 너무 큰 것 | "기후 위기 해결", "청년 실업 해결"은 6시간 프로토타입과 연결이 안 된다 |
| 서버·실시간이 핵심인 것 | 실시간 채팅, 결제, 여러 기기 동기화가 핵심이면 1박 2일에 시연이 깨진다 |
| 우리가 사용자를 모르는 것 | 근거를 못 대고, 질의에서 막힌다 |

## 5. 후보 비교 점수표 (회의 때 그대로 쓰기)

후보마다 1~5점. 합계 높은 것, 동점이면 근거 숫자가 있는 쪽.

| 질문 | 후보 1 | 후보 2 | 후보 3 |
| --- | --- | --- | --- |
| 문제 겪는 사람이 한 문장으로 그려지나 | | | |
| 근거 숫자·사례를 1시간 안에 찾을 수 있나 | | | |
| 처음 듣는 접근인가 (비슷한 서비스 없음) | | | |
| 3명 전공이 각자 한 부분씩 들어가나 | | | |
| 화면 3개, 서버 없이 시연되나 | | | |
| 시연에서 "와" 하는 장면이 하나 있나 | | | |
| 우리가 질의 3분을 버틸 수 있나 | | | |
| **합계 (35점 만점)** | | | |

Codex에게 같은 평가를 시키려면 `guide/prompts.md` **0-2번**.

## 6. 고른 뒤 다듬는 질문 5개

1. **누가**: 나이, 상황, 장소까지. "대학생"이 아니라 "창원대 기숙사에 사는 1학년 외국인 유학생"
2. **언제 곤란한가**: 하루 중 정확히 어느 순간인가
3. **지금은 어떻게 하나**: 그 방법이 왜 부족한가 (시간, 언어, 비용, 접근성)
4. **우리 서비스를 쓰면 무엇이 몇만큼 줄어드나**: 12분 → 3분, 월 2회 실수 → 0회
5. **실서비스가 되면 누가 도입하나**: 학교, 지자체, 기업, 기관. 유지 방법 한 문장

## 7. 한 줄 정의 템플릿

> **[구체적인 사람]**이 **[곤란한 순간]**에 **[우리 서비스의 핵심 행동]**으로 **[측정 가능한 변화]**를 얻게 하는 서비스

예) 거제 조선소에 갓 입사한 외국인 근로자가 작업 전 안전 점검을 할 때, 모국어 그림 체크리스트로 3분 안에 점검을 끝내게 하는 서비스

이 문장이 발표 1번 슬라이드, 꾸럼e 기획지 첫 줄, `docs/idea-brief.md` 1번이 된다.

## 8. "AI·SW 경진대회"라는 점

- 대회 이름에 AI가 들어간다. 서비스 안에 AI가 **어디에, 왜** 들어가는지 한 문장은 있어야 한다
- 다만 프로토타입에서 실제 AI를 붙일 필요는 없다. 규칙 기반으로 흐름을 보여주고 "실서비스는 LLM으로 [무엇]을 한다"고 구조를 설명하는 쪽이 실현 가능성 점수에 낫다
- 개발 과정에서 Codex를 어떻게 썼는지도 AI 활용으로 말할 수 있다 (발표 7번 슬라이드)
