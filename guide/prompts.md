## 1. 아이디어 → 명세 (가장 중요, 아이디어 확정 직후 1회)

B가 `docs/idea-brief.md`를 채운 뒤 붙여넣는다. 이 한 번으로 기능 선택, 구현 방식, 구현 순서별 지시문, 시연 시나리오, 예상 질문과 답이 `docs/spec.md`에 나온다.

```
docs/idea-brief.md, docs/FEATURE_CATALOG.md, docs/QNA.md, DESIGN.md를 읽고 docs/spec.md를 새로 작성해줘. 코드는 아직 고치지 마.

spec.md 목차:
1. 한 줄 정의 / 대상 사용자 / 해결할 문제 (idea-brief 그대로 요약)
2. 기능 선택: 카탈로그에서 핵심 3개 + 보조 최대 2개. 기능마다 [F번호, Lv1 또는 Lv2, 고른 이유 1줄, 우리 서비스에서의 구체적 동작 2줄]. Lv2는 최대 1개.
3. 화면 목록과 이동 흐름: 화면 3~5개, 각 화면의 data-screen 이름, 들어갈 컴포넌트, 다음 화면
4. 데이터 구조: data.js에 들어갈 배열·객체의 필드 이름과 타입, 예시 1건
5. 구현 순서: 6~8단계. 단계마다 (a) 목표 (b) 완료 확인 방법 (c) 그대로 붙여넣을 Codex 지시문
6. 시연 시나리오 90초: 클릭 순서대로, 각 단계에서 발표자가 할 말 1줄
7. 디자인 값: idea-brief의 디자인 레퍼런스에 맞춘 포인트 색·글꼴·모서리 토큰 값 (레퍼런스가 비어 있으면 Mobbin 검색어 3개 추천)
8. 예상 질문 10개와 30초 답변: 결론→근거→한계→계획 구조. 기술 4개(보안·데이터·구조·AI 사용 포함) / 기획 3개 / 실현 가능성·확장 3개. 답변 담당(A/B/C) 표시
9. 리스크와 대체안: 막힐 수 있는 지점 3개와 Lv1 후퇴 방법
10. 발표 슬라이드별 핵심 문장: 표지, 문제, 기존 한계, 해결, 전공 융합, 시연, 개발 과정, 기대 효과, 마무리

idea-brief에 없는 사실(통계, 출처, 인터뷰 결과)은 지어내지 말고 "[확인 필요]"로 표시해줘.
```

명세가 나오면 셋이 5분 검토 → 고칠 점을 말로 지시 → 확정 커밋.

> 같은 지시문은 Claude나 ChatGPT 채팅에 idea-brief 내용과 함께 붙여넣어도 된다. Codex가 아직 연결 안 됐을 때 쓰는 우회로.

## 3. 기능 구현 (spec.md 5번의 지시문을 순서대로)

spec에 단계별 지시문이 있으니 그걸 그대로 쓴다. 직접 쓸 때 형식:

```
spec.md 5번의 [n]단계: [기능 이름]을 구현해줘.
- 흐름: [화면A]에서 [입력] → [버튼] → [화면B]에 [결과]
- 규칙: [계산·판단 규칙]. 규칙 데이터는 js/data.js에 분리.
- 빈 상태, 잘못된 입력 안내, 저장 후 토스트 포함.
끝나면 확인 방법 알려줘.
```
